1. Scope, status, and platform boundaries

This guide describes source version 0.1.1 of the native Dart package proofchain_sdk. Its canonical public entrypoint is package:proofchain_sdk/proofchain_sdk.dart; the existing proofchain.dart entrypoint exports the same API. The package mirrors the JavaScript SDK's API surface and wire behavior; it is not a JavaScript bridge and does not run Node.js.

1.1 What you can build

Use the package from Flutter on Android/iOS or from a native Dart VM application. Its transport uses dart:io; Flutter Web and browser Dart are not supported. The package requires Dart >=3.4.0 <4.0.0 and has no runtime package dependencies. A Flutter app still depends on the Flutter SDK normally.

The main client exposes REST resources, including users, events, quests, rewards, passports, credentials, and wallet REST operations. Native server-sent events (SSE) are available through the notification client. SSE is an application connection, not FCM/APNs push delivery, and does not imply reliable background execution on a phone. The separate embedded wallet-sdk is outside this package and this guide. ProofChain.wallets does not establish an embedded signing UI or local private-key custody.

1.2 Evidence and limits

Before this documentation task, the implementation was reported as passing analysis under Dart 3.13.5, 17 behavior tests, and 583 runtime parity scenarios against the local JS SDK. Those are prior implementation results, not checks run while writing these chapters. Android/iOS builds, physical devices, and platform lifecycle behavior have not been verified by that evidence. A successful parity case also does not establish that a particular production JWT may call an endpoint: the server still decides authorization.

Examples use replaceable synthetic fixtures such as tenant slug acme, tenant identifier tenant-demo, user identifier user-demo, and quest identifier quest-demo. These are not provisioned accounts. Obtain real identifiers and an appropriately scoped JWT through your existing authenticated application flow. Never copy a privileged API key into a mobile application to make an example succeed.

2. Install the package and configure networking

2.1 Use a published release or a reviewed local checkout

The package is available on pub.dev. In your app's pubspec.yaml, merge this dependency into the existing dependencies section:

dependencies:
  flutter:
    sdk: flutter
  proofchain_sdk: ^0.1.0

The constraint accepts compatible published 0.1.x releases. A GitHub push does not publish a new registry version. To use source changes that have not yet been released, clone the public Flutter SDK repository beside your app instead:

workspace/
  mobile_app/
    pubspec.yaml
    lib/
  proofchain-flutter-sdk/
    pubspec.yaml
    lib/proofchain_sdk.dart

Replace the registry dependency with a path dependency; do not declare both:

dependencies:
  flutter:
    sdk: flutter
  proofchain_sdk:
    path: ../proofchain-flutter-sdk

The path is relative to the app's pubspec.yaml, not the shell's working directory. From workspace/mobile_app, run:

flutter pub get

For a native Dart application, omit the Flutter SDK dependency and run dart pub get from that application's root. Import a public entrypoint rather than lib/src files. Path dependencies reflect the local checkout, so pin and review the source used by your team and CI.

2.2 Android: grant Internet access in the main manifest

In the app's android/app/src/main/AndroidManifest.xml, add the Internet permission as a direct child of the existing manifest element, outside application. A permission present only in a debug manifest does not establish release-app access.

<uses-permission android:name="android.permission.INTERNET" />

This is a manifest declaration, not a runtime permission prompt. Use HTTPS and normal certificate verification. Do not broadly enable cleartext traffic to work around a deployment or certificate problem.

2.3 iOS: keep HTTPS and transport security intact

The default service URLs use HTTPS. Use a trusted HTTPS endpoint for custom baseUrl values as well. Do not add NSAllowsArbitraryLoads, disable certificate verification, or add broad App Transport Security exceptions for this SDK. The package does not configure your app's Info.plist, signing, deployment target, or network entitlements. Check device reachability and certificate trust in your app's environment; a desktop Dart request is not an iOS deployment test.

3. Choose routing, credentials, and client lifetime

3.1 Endpoint precedence

ProofChain(ProofChainOptions(...)) selects its base URL in this order:

  1. A nonempty baseUrl, used explicitly.
  2. Otherwise a nonempty tenant slug, expanded by tenantApiUrl(tenant) to https://<slug>.proofchain.co.za/api.
  3. Otherwise https://api.proofchain.co.za.

One trailing slash is removed. The SDK appends resource paths to that base; it does not automatically add /api to an explicit URL. For example, an explicit https://acme.proofchain.co.za/api keeps the /api path. Configure the exact base agreed with your service operator.

tenant is a hostname-routing slug. tenantId is the tenant identity sent with an end-user bearer token; they are not interchangeable. Setting tenantId alone does not change the base URL. forEndUser accepts tenantId and an optional explicit baseUrl, but no tenant slug argument.

ProofChainOptions field Type Default / behavior
apiKey String? Unset; nonempty value sends X-API-Key. Trusted backend only.
userToken String? Unset; nonempty value sends Authorization: Bearer ….
tenantId String? Unset; sends X-Tenant-ID only when both token and tenant ID are nonempty.
baseUrl String? Explicit endpoint; wins over tenant. Empty string falls through.
tenant String? Optional routing slug; wins over the global default.
timeout num? Milliseconds; omitted or zero uses 30000, converted to an integer.
maxRetries num? 3; 0 disables transport network-error retries.

Use sensible positive integer timeout values and nonnegative integer retry counts even though the signatures use num. Timeout covers opening a connection, sending the request, redirects, and obtaining response headers; it is not a whole-response-body or full-operation deadline. Retry delays add elapsed time.

The shared HTTP transport retries network failures, not HTTP status responses. It does not automatically retry 429, 401, 403, or 5xx responses, and its typed TimeoutError is not retried by that network-failure loop. The default permits up to three retries after the initial transport attempt. See chapter 5 before allowing retries around writes.

3.2 Mobile: use an end-user JWT

Your authenticated host supplies the JWT, tenant ID, and user identity. The SDK does not implement login, exchange credentials for tokens, store tokens, refresh tokens, or select a secure-storage package. Token acquisition and persistence remain application/backend responsibilities. Do not log tokens or put them in source code, assets, crash reports, URLs, or production build-time defines.

This standalone library creates a client from already acquired credentials. It makes no network request; its caller owns and must close the returned client. baseUrl should come from trusted application configuration, not untrusted UI input. Credentials are sent to that endpoint.

import 'package:proofchain_sdk/proofchain.dart';

ProofChain createMobileClient({
  required String jwt,
  required String tenantId,
  String? baseUrl,
}) {
  return ProofChain.forEndUser(
    userToken: jwt,
    tenantId: tenantId,
    baseUrl: baseUrl,
    timeout: 30000,
    maxRetries: 0,
  );
}

The JWT is a capability, not proof that every resource is accessible. A particular read or write can still receive 403. This example chooses zero network retries to make transport replay an explicit application decision; that is not an assertion that all reads require zero retries.

Client credentials are fixed at construction. On refresh or account/tenant switch, stop subscriptions using the old credentials, replace the main ProofChain client, and restart only the subscriptions the new session may use. ProofChain.close() closes its notifications and HTTP transport. Explicitly cancel any app-owned stream listeners/timers as well. Do not keep resource objects from the old client and expect them to pick up a new token. Closing is resource cleanup, not a public per-request cancellation API or a guarantee that a write already accepted by the server was rolled back.

3.3 Backend-only API keys and environment configuration

Use privileged API keys only in a trusted server or administrative Dart VM process. Mobile binaries, obfuscation, and build defines cannot keep such keys secret. Although the generic options allow both auth fields, do not combine a privileged key with an end-user token to bypass mobile authorization.

ProofChain.fromEnv() reads exactly PROOFCHAIN_API_KEY and PROOFCHAIN_BASE_URL from Platform.environment. It throws StateError if the API key is absent or empty. It does not load .env files, read --dart-define, or read JWT, tenant ID, tenant slug, timeout, or retry environment variables. Supply those through explicit options when needed. Environment configuration is for the trusted Dart process, not a mobile secret-injection strategy.

This standalone backend program uses the deployment-provided environment. Its tenantInfo() call requires authorization. No credentials are embedded:

import 'dart:io' show exitCode, stderr;
import 'package:proofchain_sdk/proofchain.dart';

Future<void> main() async {
  ProofChain? client;
  try {
    client = ProofChain.fromEnv();
    await client.tenantInfo();
    print('Authorized tenant information was received.');
  } catch (_) {
    stderr.writeln('Tenant lookup failed. Check configuration and credentials.');
    exitCode = 1;
  } finally {
    client?.close();
  }
}

4. Read data and integrate an authenticated Flutter screen

4.1 First executable API read

This complete native Dart program takes an ephemeral local-demo JWT, tenant ID, and known external user ID as arguments. It reads users.get(externalId); getByInternalId is a different method. Run it only with a disposable demo token in a controlled local environment: command arguments can appear in process listings or shell history and are not a production credential channel. The program deliberately does not print the user payload or token.

Save as bin/read_user.dart in a Dart/Flutter project with the path dependency. Invoke with three actual demo arguments using dart run bin/read_user.dart. There are no bundled credentials, fake responses, or authentication endpoints. The token must be authorized to read the supplied external user.

import 'dart:io' show exitCode, stderr;
import 'package:proofchain_sdk/proofchain.dart';

Future<void> main(List<String> args) async {
  if (args.length != 3) {
    stderr.writeln('Expected a local-demo JWT, tenant ID, and external user ID.');
    exitCode = 64;
    return;
  }
  final client = ProofChain.forEndUser(
    userToken: args[0],
    tenantId: args[1],
    maxRetries: 0,
  );
  try {
    final user = await client.users.get(args[2]);
    print('User read completed; status: ${user.status}');
  } catch (_) {
    stderr.writeln('User read failed. Check the demo session and permissions.');
    exitCode = 1;
  } finally {
    client.close();
  }
}

Creation occurs before try because no owned client exists if construction fails. Once construction succeeds, finally runs for both successful reads and exceptions. In a long-lived app, retain a client for the authenticated session rather than constructing and closing one in every widget build.

4.2 Flutter integration: a complete authenticated screen library

The following is Flutter-only code. Save it as lib/proofchain_app.dart in a Flutter app with the Flutter SDK and proofchain_sdk path dependencies. It is a complete library, not a replacement authentication implementation.

buildProofChainApp is the entry into an existing authenticated bootstrap: call it instead of that bootstrap's existing runApp once it has a real JWT, tenant ID, and user ID. It calls runApp itself; do not nest it inside another widget builder. It intentionally has no invented main or login API. A host that already owns the top-level MaterialApp can instead mount ProofChainEventsScreen under that app, supplying the same constructor values.

Here userId is the user identifier expected by the events API, not automatically a users.get external ID. Use the correct identity from your host's authorized session/domain mapping. This requests the first 20 matching events, not a complete paginated history. The server must permit the JWT to list those events.

import 'package:flutter/material.dart';
import 'package:proofchain_sdk/proofchain.dart' as pc;

void buildProofChainApp({
  required String jwt,
  required String tenantId,
  required String userId,
  String? baseUrl,
}) {
  WidgetsFlutterBinding.ensureInitialized();
  runApp(MaterialApp(
    title: 'ProofChain activity',
    home: ProofChainEventsScreen(
      jwt: jwt,
      tenantId: tenantId,
      userId: userId,
      baseUrl: baseUrl,
    ),
  ));
}

class ProofChainEventsScreen extends StatefulWidget {
  const ProofChainEventsScreen({
    super.key,
    required this.jwt,
    required this.tenantId,
    required this.userId,
    this.baseUrl,
  });

  final String jwt;
  final String tenantId;
  final String userId;
  final String? baseUrl;

  @override
  State<ProofChainEventsScreen> createState() => _EventsState();
}

class _EventsState extends State<ProofChainEventsScreen> {
  late pc.ProofChain _client;
  late Future<List<pc.Event>> _events;

  @override
  void initState() {
    super.initState();
    _openSession();
  }

  void _openSession() {
    _client = pc.ProofChain.forEndUser(
      userToken: widget.jwt,
      tenantId: widget.tenantId,
      baseUrl: widget.baseUrl,
      maxRetries: 0,
    );
    _events = _readEvents();
  }

  Future<List<pc.Event>> _readEvents() {
    return _client.events.list(pc.ListEventsRequest(
      userId: widget.userId,
      limit: 20,
    ));
  }

  @override
  void didUpdateWidget(covariant ProofChainEventsScreen oldWidget) {
    super.didUpdateWidget(oldWidget);
    if (oldWidget.jwt != widget.jwt ||
        oldWidget.tenantId != widget.tenantId ||
        oldWidget.userId != widget.userId ||
        oldWidget.baseUrl != widget.baseUrl) {
      _client.close();
      _openSession();
    }
  }

  void _reload() {
    if (!mounted) return;
    setState(() {
      _events = _readEvents();
    });
  }

  @override
  void dispose() {
    _client.close();
    super.dispose();
  }

  String _errorMessage(Object? error) {
    if (error is pc.AuthenticationError) {
      return 'Your session needs attention. Return to sign-in.';
    }
    if (error is pc.AuthorizationError) {
      return 'This session cannot view these events.';
    }
    if (error is pc.RateLimitError) {
      return 'Too many requests. Wait before trying again.';
    }
    if (error is pc.NetworkError || error is pc.TimeoutError) {
      return 'Could not reach the service. Check your connection.';
    }
    return 'Events could not be loaded.';
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Recent activity')),
      body: FutureBuilder<List<pc.Event>>(
        future: _events,
        builder: (context, snapshot) {
          if (snapshot.connectionState != ConnectionState.done) {
            return const Center(child: CircularProgressIndicator());
          }
          if (snapshot.hasError) {
            return Center(
              child: Column(
                mainAxisSize: MainAxisSize.min,
                children: [
                  Text(_errorMessage(snapshot.error)),
                  TextButton(
                    onPressed: _reload,
                    child: const Text('Try read again'),
                  ),
                ],
              ),
            );
          }
          final events = snapshot.data ?? const <pc.Event>[];
          if (events.isEmpty) {
            return const Center(child: Text('No recent events.'));
          }
          return ListView.builder(
            itemCount: events.length,
            itemBuilder: (context, index) {
              final event = events[index];
              return ListTile(
                title: Text(event.eventType),
                subtitle: Text(event.timestamp),
              );
            },
          );
        },
      ),
    );
  }
}

The Future is cached in state, never created in build; layout rebuilds do not trigger repeated requests. FutureBuilder owns async rendering, so there is no manual setState after awaiting network work. The retry callback checks mounted before updating state. During reload or credential replacement, loading takes precedence over any data retained by FutureBuilder, preventing old-session data from being rendered while the new future is pending.

The screen constructs and owns its client, so it closes it in dispose and replaces it in didUpdateWidget. A host refreshes credentials by rebuilding with new constructor values; it does not mutate the old client. This screen has no subscriptions. If adding SSE later, stop old listeners before opening the replacement session and cancel app-owned subscriptions in dispose. If you instead inject a shared client, its session owner—not every child widget—must close it. Never close a host-owned shared client merely because one route exits.

5. Model, JSON, and error semantics

5.1 Typed constructors do not normalize every field name

Named TypeScript interfaces become Dart classes with named constructor arguments, getters, fromJson(JsonMap), and toJson(). Anonymous object and Partial<...> inputs generally remain JsonMap, which is Map<String, Object?>. Use the signature of the actual method rather than translating JS syntax mechanically. Optional positional method arguments remain positional: events.list(request), not events.list(request: request).

Field casing follows the source interface, not a universal Dart style rule. For example, ListEventsRequest.userId is camelCase, while UpdateEndUserRequest.display_name is snake_case. Resource methods can rename fields when preparing wire requests: events.list maps userId to user_id. Do not apply a global casing transform to models or manually rename typed constructor arguments.

Reserved source names are mapped where necessary. SchemaField.defaultValue is the Dart property for the JSON key default. SchemaField.required is actually named required; do not invent a required_ property. This standalone serialization example performs no network operation:

import 'package:proofchain_sdk/proofchain.dart';

JsonMap schemaFieldJson() {
  const field = SchemaField(
    name: 'attendance',
    type: 'string',
    required: true,
    defaultValue: 'pending',
  );
  final decoded = SchemaField.fromJson(field.toJson());
  return decoded.toJson();
}

5.2 Omitted and explicitly null are different

For the models illustrated here, normal constructors omit optional null fields from toJson. Passing email: null to UpdateEndUserRequest therefore does not itself express an explicit JSON null. Models decoded with fromJson retain the original map for toJson, preserving explicit nulls and extra keys. For example:

import 'package:proofchain_sdk/proofchain.dart';

Map<String, JsonMap> compareUpdatePayloads() {
  const omitted = UpdateEndUserRequest(email: null);
  final explicit = UpdateEndUserRequest.fromJson(
    <String, Object?>{'email': null},
  );
  return {
    'omitted': omitted.toJson(),
    'explicit': explicit.toJson(),
  };
}

The returned omitted payload has no email key; explicit contains that key with a null value. This is a serialization distinction, not a promise that the backend allows clearing an email. Field-level null/clear semantics still belong to the endpoint contract and server validation.

Do not use fromJson as a schema validator. Incorrect field types can cause cast errors during decoding; missing required fields can cause errors when required getters are accessed. Treat the input map as immutable after decoding: retained original maps are not deep-copied, and mutating them is not a reliable way to update already decoded getters. To derive a request, construct a new model or a new map. toJson output may contain personal data; do not log entire responses by default.

5.3 Partial updates use explicit maps

quests.update(String questId, JsonMap data) accepts a partial object and uses HTTP PUT internally. Do not infer its signature from the HTTP verb, invent an UpdateQuestRequest, or send a whole fetched model when only one field should change. The following complete library accepts a configured client; its caller retains ownership. This is an authorized write, normally a trusted administrative operation. quest-demo is a replaceable fixture, not a known server record.

import 'package:proofchain_sdk/proofchain.dart';

Future<Quest> renameQuest(ProofChain client, String questId) {
  final JsonMap changes = {'name': 'Acme welcome quest'};
  return client.quests.update(questId, changes);
}

Map keys are backend/source field names. Omit a key to leave it out of the request; include a null only when the server documents that null behavior. Keep nested values JSON-compatible: strings, booleans, finite numbers, nulls, lists, maps with string keys, or supported SDK models. Do not pass arbitrary DateTime, File, or custom application objects to a JSON request. Timestamps in models are strings; parse them explicitly in your presentation layer when needed. Types expressed as num are not automatically integer-only validators.

5.4 Handle typed failures without leaking raw payloads

Catch specific errors before ProofChainError. Exceptions are not returned as success models. The shared HTTP status mapping is:

Failure SDK exception Application response
401 AuthenticationError Ask the host session manager to reauthenticate or refresh.
403 AuthorizationError Explain access denial; do not retry with a privileged mobile key.
404 NotFoundError Handle a missing record in the current authorized context.
400 or 422 ValidationError Inspect safely shaped details; correct the request.
429 RateLimitError Respect a usable delay and your application retry policy.
5xx ServerError Surface a service failure; reconcile writes before resubmission.
Other non-success status ProofChainError Inspect statusCode without assuming a known subtype.
Transport failure after network retries NetworkError Distinguish uncertain write outcome from a confirmed rejection.
Connection/header deadline exceeded TimeoutError Handle timeout; it is not evidence that a write did not run.

This table describes the main client's shared HTTP transport, not every exported helper. Standalone ingestion clients have their own timeout and lifecycle behavior; do not assume all SDK timeouts become TimeoutError.

ProofChainError exposes message, nullable statusCode, and nullable responseBody; do not assume all subclasses retain a response body. Even an error message may contain server-controlled or sensitive content. Display curated UI messages and use redacted diagnostics.

ValidationError.rawErrors is Object?: the server can send a map, string, list, null, or other shape. Its lazy errors getter expects a list of ValidationErrorDetail-shaped entries and may throw for nonstandard data. Do not blindly evaluate it inside a catch block. RateLimitError.retryAfter is nullable num in seconds, not a Duration or milliseconds. Header parsing can produce a nonfinite number for unusable input; it does not implement full HTTP-date scheduling. Check nullability, finiteness, and sign before using it.

This standalone library produces safe, bounded summaries for an application's error boundary. It handles arbitrary raw validation shapes without echoing server strings. Its return value is a message, not a retry action.

import 'package:proofchain_sdk/proofchain.dart';

int countFieldErrors(Object? raw) {
  if (raw is! List) return 0;
  var count = 0;
  for (final item in raw) {
    if (item is ValidationErrorDetail) {
      count++;
    } else if (item is Map &&
        item['field'] is String &&
        item['message'] is String) {
      count++;
    }
  }
  return count;
}

String describeFailure(Object error) {
  if (error is AuthenticationError) return 'Sign-in needs attention.';
  if (error is AuthorizationError) return 'Access is not permitted.';
  if (error is NotFoundError) return 'The requested record was not found.';
  if (error is ValidationError) {
    final count = countFieldErrors(error.rawErrors);
    return count == 0
        ? 'The request was rejected. Check the submitted values.'
        : 'The request has $count field validation issue(s).';
  }
  if (error is RateLimitError) {
    final seconds = error.retryAfter;
    if (seconds != null && seconds.isFinite && seconds >= 0) {
      return 'Rate limited; suggested wait: $seconds seconds.';
    }
    return 'Rate limited; no usable retry delay was supplied.';
  }
  if (error is TimeoutError) return 'The request timed out.';
  if (error is NetworkError) return 'A network failure occurred.';
  if (error is ServerError) return 'The service could not complete the request.';
  if (error is ProofChainError) return 'The API request failed.';
  return 'An unexpected application or response-format error occurred.';
}

A catch-all boundary is still needed for malformed successful JSON, model cast errors, and application failures, which are not necessarily wrapped in ProofChainError. Do not relabel every unexpected exception as a network error.

5.5 Avoid blind write retries

A connection can fail after the server has applied a write but before the app receives its response. The shared network retry loop is not restricted to GET; with its default retry setting, transport failures can replay writes as well. There is no general SDK idempotency-key facility or automatic write reconciliation. A timeout, socket failure, or 5xx therefore must not trigger an unconditional application-level retry of operations such as points awards, claims, wallet creation, settlement, or event creation.

For sensitive workflows, configure maxRetries: 0 when constructing the client and use an endpoint-specific reconciliation/confirmation policy supplied by your backend. Do not silently add another retry loop around a helper that already performs multiple requests. For reads, offer an explicit bounded retry or user retry after considering authorization, rate limits, and the actual failure. The Flutter screen's button retries only its event read; it is not a pattern for replaying arbitrary mutations.

6. Users, profiles, and pagination

These recipes target native Android/iOS and the Dart VM, not Flutter Web. Each Dart block is an independent library importing package:proofchain_sdk/proofchain.dart. Add the SDK dependency before using them. Functions accept an already configured ProofChain and known identifiers; the caller owns and eventually closes that client. Functions do not run merely by being imported.

Values such as acme, user-demo, quest-demo, lesson_completed, and sample metadata are replaceable fixtures, not pre-existing records or a backend protocol. Use identifiers returned by your deployment. Every request is subject to server authorization and tenant isolation. A JWT identifies an end user; it does not grant access to administrative routes. Put privileged operations in a trusted backend or explicitly authorized native administration process, never ship a privileged API key inside a mobile application.

6.1 External IDs and editable profile data

users.get, update, setProfile, and attribute helpers address the user's external ID. Methods explicitly named getByInternalId and updateByInternalId address the internal ID. delete, GDPR preview, and GDPR deletion use the internal ID. Do not exchange these identifiers just because both are strings.

A profile editor should submit only permitted fields and render the returned user, rather than assuming that a local edit was accepted. This example changes a display name and application metadata; it requires the corresponding server-authorized user scope.

import 'package:proofchain_sdk/proofchain.dart';

Future<EndUser> saveProfile(
  ProofChain client,
  String externalId,
  String displayName,
) async {
  await client.users.setProfile(
    externalId,
    SetProfileRequest(display_name: displayName, language: 'en'),
  );
  return client.users.updateAttributes(externalId, {
    'preferred_topic': 'developer-learning',
    'onboarding_version': 1,
  });
}

The SDK sends {'attributes': attributes} for updateAttributes; it does not merge the supplied map with a locally fetched copy. Confirm your server's patch semantics before relying on preservation of unrelated keys. removeAttributes reads the existing attributes, removes keys, then writes the resulting map. That read-modify-write is not atomic: concurrent editors can overwrite changes. Keep secrets and sensitive personal information out of unneeded metadata.

6.2 Backend/admin: provision users and enumerate pages

Provisioning and whole-tenant enumeration belong in authorized administration. Creation is not an upsert and the SDK does not invent a duplicate-resolution policy. An external ID should be stable within your own identity system.

import 'package:proofchain_sdk/proofchain.dart';

Future<EndUser> provisionUser(
  ProofChain admin,
  String externalId,
) {
  return admin.users.create(CreateEndUserRequest(
    external_id: externalId,
    display_name: 'Acme learner',
    attributes: {'source': 'acme-enrolment'},
  ));
}

Stream<EndUser> enumerateUsers(ProofChain admin) async* {
  num page = 1;
  while (true) {
    final result = await admin.users.list(
      ListEndUsersOptions(page: page, page_size: 50),
    );
    for (final user in result.users) {
      yield user;
    }
    if (!result.has_more) break;
    page = result.page + 1;
  }
}

EndUserListResponse exposes users, total, page, page_size, and has_more. This is page-based pagination, unlike APIs using limit/offset. The sample size of 50 is an application choice, not a documented server maximum. For large directories, consume the stream incrementally instead of retaining all users. Directory changes during traversal can affect page membership; the SDK does not provide a snapshot cursor.

Filters include search, status, segment, has_wallet, min_events, sort_by, and sort_order. Boolean false and numeric zero are retained for has_wallet and min_events. Avoid assuming every other API treats falsy options identically. users.export returns CSV/JSON bytes, not a browser download. Its options map accepts segment and format; the caller must choose where to save bytes and how to protect exported personal information.

Adding points, merging identities, linking/provisioning wallets, and GDPR operations need explicit policy and authorization. None is invoked by these recipes. In particular, do not trigger deletion while merely loading a profile.

7. Documents, binary files, certificates, and event evidence

7.1 Attest a selected document

UploadFile is an in-memory value. Obtain bytes using your app's picker or a caller-supplied native file path; the SDK does not request picker permissions. The following library additionally depends on Dart's dart:io. It reads only the supplied path and does not assume any bundled fixture file exists.

import 'dart:io';
import 'package:proofchain_sdk/proofchain.dart';

Future<AttestationResult> attestSelectedDocument(
  ProofChain client,
  String userId,
  String selectedPath,
  String filename,
) async {
  final bytes = await File(selectedPath).readAsBytes();
  return client.documents.attest(AttestRequest(
    file: UploadFile(bytes, filename: filename),
    filename: filename,
    userId: userId,
    eventType: 'document_uploaded',
    metadata: {'application': 'acme-learning'},
    encrypt: true,
  ));
}

This is a multipart request, not a JSON-encoded file. Metadata is serialized as JSON within a multipart field. encrypt: true sends encrypt=1; omitted or false does not send that flag. Encryption is a server request, not client-side cryptography or a promise about key ownership.

Set a nonempty filename explicitly in both the upload value and request. UploadFile defaults to document, but documents.attest chooses the request's filename or document, and vault upload chooses the request's filename or file. NFT minting chooses imageFilename or image.png. An UploadFile.filename alone therefore is not a universal filename override. Use contentType when known; its default is application/octet-stream.

AttestationResult contains id, ipfsHash, documentHash, gatewayUrl, verifyUrl, certificateId, status, attestationMode, and timestamp, with optional blockchainTx and proof. Preserve these distinctions: a document hash, an IPFS hash, an event ID, and a certificate ID are not interchangeable. A returned record or queued status does not by itself mean blockchain finality. documents.get(ipfsHash) returns an Event, not document bytes.

7.2 Vault storage and authenticated binary retrieval

Vault storage is a separate resource from document attestation. Uploading to the vault does not call documents.attest. The next recipe returns downloaded bytes to its caller rather than writing an arbitrary destination or opening a URL. It needs dart:typed_data in addition to the SDK dependency.

import 'dart:typed_data';
import 'package:proofchain_sdk/proofchain.dart';

Future<Uint8List> storeAndReadVaultFile(
  ProofChain client,
  String userId,
  Uint8List bytes,
  String filename,
) async {
  final stored = await client.vault.upload(VaultUploadRequest(
    file: UploadFile(bytes, filename: filename),
    filename: filename,
    userId: userId,
    accessMode: 'private',
  ));
  return client.vault.download(stored.id);
}

vault.download returns Uint8List through the configured authenticated HTTP client. It is not the gatewayUrl returned by attestation. Both upload and binary retrieval buffer data in memory; set application size limits before reading a large selected file. No SDK upload-size maximum is enforced here. Folders, moves, and expiring shares are server resources; share(fileId, expiresInHours) uses hours, not milliseconds. Share response data is JsonMap: inspect the actual server contract rather than assuming an undocumented URL key. Vault deletions are explicit operations and are not part of this recipe.

7.3 Consume certificate verification without inventing a boolean

Use the typed verification resource when you want the modeled response. certificates.verify returns a raw JsonMap; verifyResource.certificate returns CertificateVerifyResult. The typed result has status, not a valid boolean. Present the actual status, expiration, and revocation information using your product's verification policy.

import 'package:proofchain_sdk/proofchain.dart';

Future<CertificateVerifyResult> inspectCertificate(
  ProofChain client,
  String certificateId,
  void Function(String status, String? revokedAt) present,
) async {
  final result = await client.verifyResource.certificate(certificateId);
  present(result.status, result.revokedAt);
  return result;
}

The response also includes recipient/title, issue and optional expiry times, IPFS hash, verification URL, and optional blockchain metadata. A network failure is not a negative verification decision. Keep “could not check” distinct from a server-reported revoked or otherwise unacceptable certificate.

For other evidence, client.verify(ipfsHash) is the main hash verification route; verifyResource.event(ipfsHash) returns raw event verification data. eventBatchProof(eventId) retrieves a batch proof; proof(leaf, proof, root) submits explicit proof material. batch(batchId) and batchVerify(items) are different calls with different identifiers/payloads. The SDK does not locally prove authenticity merely by deserializing these responses.

8.1 Write an authorized event and search its domain

Event writes must be permitted by the server for the current caller. If an ordinary mobile user should submit only end-user ingestion events, use chapter 9 rather than granting tenant event-write privileges. A client-supplied source is metadata, not proof of authorization.

import 'package:proofchain_sdk/proofchain.dart';

9.1 Mobile JWT ingestion

Obtain a JWT from your existing authorized identity flow; this SDK does not define a login route. Pass the tenant and API origin belonging to that identity. apiUrl is the API origin used before the /end-user/... path, not the main client's tenant-prefixed resource URL.

import 'package:proofchain_sdk/proofchain.dart';

Future<IngestEventResponse> ingestMobileLesson(
  String userToken,
  String tenantId,
  String apiOrigin,
  String userId,
  String lessonId,
) async {
  final ingestion = EndUserIngestionClient(EndUserIngestionClientOptions(
    userToken: userToken,
    tenantId: tenantId,
    apiUrl: apiOrigin,
    timeout: 30000,
  ));
  return ingestion.ingest(IngestEventRequest(
    userId: userId,
    eventType: 'lesson_completed',
    data: {'lesson_id': lessonId},
    timestamp: DateTime.now().toUtc().toIso8601String(),

}

setToken(newToken) updates a retained end-user ingestion client after your identity layer refreshes credentials. It does not refresh tokens itself. 9.2 Backend/admin: direct ingestion with schema selection

The API key in this recipe must come from trusted runtime configuration. Never compile it into a mobile binary, include it in a checked-in example, or return it from an application backend to an untrusted client.

import 'package:proofchain_sdk/proofchain.dart';

Future<IngestEventResponse> ingestTrustedLesson(
  String apiKey,
  String ingestOrigin,
  String userId,

A nonempty schemaIds list becomes the comma-separated X-Schemas header for direct single-event ingestion only. Direct batches ignore per-event schema IDs. End-user ingestion ignores both schema IDs and eventSource; adding them does not grant privileged provenance. hot: true is sent when requested; hot: false is omitted. timestamp is an optional caller-supplied string; the SDK does not infer a domain timestamp or validate its semantics.

9.3 Batch accounting and limits

Do not confuse successful HTTP delivery with all events being queued or confirmed. Consume totalEvents, queued, failed, and individual results. The normalized per-event fields are eventId, certificateId, and status. Single responses can additionally expose queuePosition and estimatedConfirmation; those queue fields are not retained in batch results.

import 'package:proofchain_sdk/proofchain.dart';

Future<BatchIngestResponse> ingestMobileBatch(
  EndUserIngestionClient ingestion,
  List<IngestEventRequest> events,
  void Function(num queued, num failed) presentCounts,
) async {
  if (events.length > 100) {
    throw ArgumentError.value(events.length, 'events', 'Maximum is 100');
  }
  final result = await ingestion.ingestBatch(
    BatchIngestRequest(events: events),
  );
  presentCounts(result.queued, result.failed);
  return result;
}

For direct ingestion, use the same BatchIngestRequest with IngestionClient.ingestBatch, up to 1,000 events. Oversized batches throw ValidationError before sending. The SDK does not enforce a nonempty minimum. Partition larger work in the application and preserve each batch's outcome; do not assume atomicity, automatic rollback, or a backend idempotency key.

timeout is in milliseconds and defaults to 30,000 when omitted or falsy. Batch calls use twice the configured timeout. Unlike the shared HTTP client's connection/header deadline, standalone ingestion applies its timeout to the whole operation, including response-body reading, and closes that operation's transport on timeout. ingest and ingestBatch report timeout as NetworkError. Direct getEventStatus(eventId) returns the raw wire-keyed JsonMap, uses the single timeout, and can throw dart:async TimeoutException instead. End-user ingestion has no status method.

Neither mode retries automatically, including network errors or HTTP 429. Handle RateLimitError and transient failures at an application boundary; an ambiguous write failure can mean the server already accepted the event. Do not infer a universal retry-safe property from the request returning an exception. The shared resource HTTP client retries network errors, not HTTP status responses; that separate behavior does not apply to these clients.

11.3 Backend/admin: provisioning and sensitive wallet operations

Wallet creation/dual creation, NFT registration, token administration, transfers/swaps, key export, and passport points/template/badge/achievement mutations must be restricted to server-authorized workflows. 12. Native notifications and foreground lifecycle

12.1 Subscribe to native SSE and retain the cancellation handle

notifications.subscribe opens a native Server-Sent Events connection and returns an Unsubscribe function immediately. It is not a future and should not be awaited. The positional third argument is SubscribeOptions. This controller needs only the SDK dependency and makes lifecycle ownership explicit.

import 'package:proofchain_sdk/proofchain.dart';

class ForegroundNotifications {
  final ProofChain client;
  final String userId;
  final NotificationCallback onEvent;
  final void Function(String state) onState;
  Unsubscribe? _cancel;

  ForegroundNotifications({
    required this.client,
    required this.userId,
    required this.onEvent,
    required this.onState,
  });

  void resume() {
    if (_cancel != null) return;
    _cancel = client.notifications.subscribe(
      userId,
      onEvent,
      SubscribeOptions(
        onConnect: () => onState('connected'),
        onDisconnect: () => onState('disconnected'),
        onError: (error) => onState('notification parse failure'),
        autoReconnect: true,
        reconnectDelay: 3000,
      ),
    );
  }

  void pause() {
    _cancel?.call();
    _cancel = null;
  }

  void dispose() {
    pause();
  }
}

Connect the controller's resume() to the application's foreground/resumed lifecycle and call pause() when the owner leaves foreground (including hidden, inactive, paused, or detached states according to your application policy). In Flutter, a WidgetsBindingObserver or AppLifecycleListener in the owning widget/service can forward those transitions; remove that observer/listener in its disposal method. Create one controller per intended subscription owner, not inside build(). A controller for a shared client cancels only its subscription; it must not close the entire client when another screen still uses it.

On returning to foreground, refresh authoritative domain data as well as resubscribing. Mobile operating systems can suspend or terminate an application; SSE is not guaranteed background delivery. The client does not persist a notification cursor, send Last-Event-ID, or guarantee replay of missed events. Deduplicate/update UI using your domain records rather than assuming exactly-once notification delivery.

12.2 Callback semantics and reconnect behavior

NotificationEvent exposes id, event, data, tenant_id, user_id, and timestamp. Treat data as event-specific metadata; reload records when a workflow needs authoritative status. Do not mutate privileged server state just because a notification named an event.

The options have deliberately narrow semantics:

Option Actual behavior
onConnect Called when a parsed JSON payload has event: connected, not merely when TCP/HTTP connects
onDisconnect Called after failed connection, stream error, or stream end
onError Reports notification JSON/model parsing or callback-processing failures; not a general transport-error callback
autoReconnect Defaults to true; false closes after a disconnect
reconnectDelay Fixed delay in milliseconds, default 3,000; not exponential backoff

Only unnamed SSE messages or SSE event: message are dispatched. Other named SSE event types are ignored, and comment lines are ignored. The JSON event field inside an accepted message is distinct from the SSE event-line name. Malformed data is reported through onError; the SDK does not forward the underlying connection exception there. Keep callbacks short, synchronous, and nonthrowing; schedule longer application work separately with its own error handling.

Calling the unsubscribe function cancels connecting, connected, and reconnecting work, aborts pending requests, closes the dedicated native transport, and stops its timer. It is safe to call repeatedly. Explicit cancellation does not need a server-side unsubscribe request. notifications.close() cancels every active subscription owned by that resource and prevents future subscriptions; it does not close the shared HTTP client. ProofChain.close() closes notifications and the shared HTTP transport and is the final owner-level cleanup.

The SSE URL carries query authentication: api_key when configured, or token and optional tenant_id for user authentication. Use HTTPS and avoid logging full URLs in application logs, proxies, analytics, or crash reports. For mobile, use the least-privileged user-token client, never an embedded tenant API key. SSE reconnection reads the client's configured credentials; the main client has no token setter. When credentials change, cancel the old subscription and replace/reconfigure the owning main client through your identity lifecycle.

12.3 Browser Web Push is not native push

The SDK retains server-side Web Push compatibility APIs: getVapidKey, registerPush, unregisterPush, and generateServiceWorker. A VAPID key and a PushSubscriptionJSON are browser Web Push concepts, not FCM/APNs device tokens. Registering arbitrary native strings as a browser subscription does not enable mobile delivery.

On native Android/iOS, requestPermissionAndSubscribe returns null. It does not request OS notification permission, create a service worker, contact PushManager, or substitute Firebase Cloud Messaging or Apple Push Notification service. generateServiceWorker returns JavaScript source as a string; native Dart does not execute it. getVapidKey returns null on any caught failure, so null is not proof that Web Push is intentionally disabled on the server.

Implement native background push separately with your application's actual FCM/APNs infrastructure and backend contract if required. This SDK has no native device-token registration route or permission bridge to demonstrate. Do not promise a background notification merely because foreground SSE works.

These recipes document the implemented source surface. Prior SDK evidence was clean Dart 3.13.5 analysis, 17 behavior tests, and 583 runtime parity scenarios; those are prior implementation checks, not checks run while writing this chapter. Android/iOS builds and real-device behavior remain unverified.

13. Production integration and security

13.1 Ownership and the application boundary

Use a session-scoped ProofChain instance, not a new instance in every widget build(). It owns the shared native HTTP connection pool and notification subscriptions. Resource objects such as client.users are views over that client's transport and credentials, not independently authenticated sessions. Pass the configured client into repositories/services that need it. A method that accepts a caller-owned client should not close it; the session owner closes it on sign-out, replacement, or final disposal.

A foreground notification owner should cancel its Unsubscribe callback when the screen/session is no longer active. The SDK does not observe Flutter's lifecycle for you. If your policy pauses streaming when the app leaves the foreground, connect that cancellation to your app's WidgetsBindingObserver or existing lifecycle controller, then create a new subscription on resume. Do not assume a native SSE socket will survive background suspension. Renew authentication before reconnecting if the session has expired.

The two ingestion clients do not share the main client, do not have close() methods, and own an HTTP transport per operation. EndUserIngestionClient.setToken() affects subsequent requests; it does not retroactively change an in-flight request. There is no corresponding token setter on the main ProofChain client.

Concern Application rule
Tenant/admin API keys Keep in trusted backend/native administrative processes only. Never ship them in app assets, source, build defines or obfuscated binaries.

SSE query authentication is a compatibility constraint. notifications.subscribe() builds a stream URL containing user_id plus token/tenant_id for JWT authentication, or api_key for API-key authentication. That matches the current JavaScript protocol. The application should not manually assemble or log this URL; configure reverse proxies, telemetry and access-log pipelines to redact these parameters. Never use privileged-key streaming inside a distributed mobile app.

Credentials are sent to the configured origin. The main ProofChain shared HTTP transport follows same-origin redirects and refuses authenticated cross-origin redirects. Standalone ingestion and native SSE use separate transports and do not implement that same explicit redirect guard; configure their approved endpoints and proxies not to redirect credentials across origins. Fix routing rather than weakening certificate verification. This SDK provides no certificate-pinning configuration hook.

13.3 Write semantics, duplicates and concurrent edits

The default shared transport permits network-error retries. A connection failure can occur after a server has accepted a mutation but before the client sees the response. Retrying that mutation may duplicate a user, event, issuance, payment-related operation or mint. maxRetries: 0 disables this shared transport replay; it does not make a write atomic or prove that a failed request had no effect. Do not add blind outer retries around writes. Reconcile with authoritative server state or use an explicit backend-provided idempotency contract when that endpoint actually supports one; the SDK does not invent an idempotency key protocol.

The following helpers are not transactions:

  • events.createBatch() calls individual creates sequentially. If an intermediate request fails, earlier events may already exist. It is not the standalone ingestion batch endpoint.
  • Quest step helpers read the quest and replace its steps array. Concurrent administrators can overwrite each other's edits. Serialize editing or use a backend concurrency policy; no optimistic version check is added by the SDK.
  • quests.reorderSteps() submits the IDs you pass. Supply the complete intended set in the desired order; omitted steps are not automatically preserved by that replacement. Unknown IDs throw before the update, but the helper is not a general duplicate/completeness validator.
  • users.removeAttributes() reads attributes and patches a modified object. Coordinate concurrent updates rather than treating it as a field-level atomic removal endpoint.
  • users.ensureWallet() may create wallets. Its inherited JavaScript behavior falls back to dual-wallet creation after lookup/single-wallet errors, not only after a not-found result. Do not treat it as a side-effect-free probe or proof of exactly-once provisioning.

Concurrent identical GET requests on one main client share an in-flight request. Once it settles, the entry is removed: this is neither persistent response caching nor a freshness/TTL policy. Mutations are not coalesced, and separate ProofChain instances do not share that in-flight map.

Path Timeout/retry behavior

14.3 Platform behavior that must not be mistaken for parity

The port mirrors the current local JavaScript API, not every browser capability or every possible backend version. Native users.export() uses the SDK's configured base URL and credentials instead of browser-relative fetch and returns Uint8List. The main client's shared HTTP transport deliberately refuses authenticated cross-origin redirects; this is not a blanket guarantee for standalone ingestion or SSE. Dart URI normalization may render RFC3986-equivalent unreserved characters differently without changing the URL's meaning.

requestPermissionAndSubscribe() does not request Android/iOS notification permission and returns null. Generated service-worker source is for a separate browser deployment, not a native isolate. FCM/APNs integration, reliable background delivery, embedded wallet signing/provider UX, login/token refresh, offline persistence/queues and Flutter Web are not supplied by this package. Do not label an app as supporting these simply because an adjacent REST method exists.
